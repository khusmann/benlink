# Vero VR-N76 — Field Notes

Findings from a first successful benlink session against a **Vero VR-N76**
(firmware ~0.7.x, HW ver reported by device) using BLE on **macOS 26.5 (Tahoe)**
with `bleak` via CoreBluetooth. Contributed by KC9MHE, 2026-07-03.

## What worked

- **BLE connect** via `RadioController.new_ble(<peripheral-uuid>)`
- Read: `device_info`, `status`, `settings`, `battery_level`, `channels`
- Write: `set_channel(...)` for name, RX/TX freq, CTCSS tones, bandwidth,
  `tx_disable`, `scan` — all round-tripped correctly and persisted after
  power-cycle.
- ~32-channel table on the currently-selected region parsed cleanly.

## What broke (and how)

Every parse crash was a strict `_pad: t.Literal[0]` field. The N76 sets
non-zero bits in several of them, presumably because Vero's firmware carries
capability flags that upstream benlink hasn't mapped yet.

| Struct       | Field  | Width | Observed value | File |
|--------------|--------|-------|----------------|------|
| `DevInfo`    | `_pad` | 2 bit | non-zero (exact value not captured; pre-refactor 4-bit field observed `4`) | `dev_info.py` |
| `Status`     | `_pad` | 2 bit | non-zero | `status.py` |
| `RfCh`       | `_pad` | 4 bit | non-zero on some channel entries | `rf_ch.py` |
| `SetPhoneStatusBody` | `_pad`/`_pad2` | 1 / 14 bit | not yet exercised — loosened defensively | `phone_status.py` |

**Fix applied in this branch:** each `_pad` was changed from
`t.Literal[0] = bf_lit_int(N, default=0)` to `int = bf_int(N, default=0)`.

Reads still succeed (extra bits are silently accepted). Writes still emit
zeros in those bit positions, matching the pre-existing protocol assumption.
When the maintainer eventually reverse-engineers what those bits mean, they
can be extracted as named `bool`/`int` fields without breaking existing
callers.

## macOS quirks worth documenting

1. **CoreBluetooth uses peripheral UUIDs, not MAC addresses.** The physical
   MAC that the radio advertises (`38:D2:xx:xx:xx:xx` in this case) will
   *not* work as an argument to `RadioController.new_ble()`. Discover with
   `BleakScanner.discover()` and use the UUID it returns
   (`XXXXXXXX-XXXX-XXXX-XXXX-XXXXXXXXXXXX`).
2. **Classic BT pairing hides BLE ads.** The N76 advertises as a
   Handsfree/Headset device on Bluetooth Classic (used for the wireless-mic
   accessory audio). If you pair it via System Settings for classic BT,
   CoreBluetooth may filter its BLE advertisement out of the discovery scan.
   **Unpair the classic connection** before scanning with `bleak`.
3. **BLE authorization is per-process on macOS.** Terminal, iTerm, VSCode
   etc. each need their own "allow Bluetooth" grant. SSH sessions inherit
   no grant and get `BleakBluetoothNotAvailableError: DENIED_BY_UNKNOWN`
   — run locally, not over SSH.

## What benlink does *not* yet expose for the N76

- **Regions / channel banks.** The N76 has 12 selectable regions, each with
  its own 32-channel table and a name. Protocol enums exist
  (`READ_REGION_NAME=73`, `WRITE_REGION_CH=58`, `WRITE_REGION_NAME=59`,
  `SET_REGION=60`), and `Status.curr_region` is already parsed, but the
  request/reply bodies for these opcodes are not implemented. See ROADMAP.
- **DevInfo undocumented flag bits** (`_pad`). Unknown meaning; observed
  non-zero.
- **AIS / marine channels.** N76 handles them fine; nothing benlink-specific
  needed.

## Reproducing the test session

```python
import asyncio
from benlink.controller import RadioController

UUID = "377F7AC2-2AA3-D0F4-8DDC-D89A4C3594C6"  # substitute yours

async def main():
    async with RadioController.new_ble(UUID) as radio:
        print(radio.device_info)
        print(radio.status)
        print(f"channels: {len(radio.channels)}")
        for i, ch in enumerate(radio.channels[:5]):
            print(f"  [{i}] {ch}")

asyncio.run(main())
```
